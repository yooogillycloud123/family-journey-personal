## Functional changes and causal evidence
1. **Fixed compositor geometry**: Native 3-page photo/video `stage` now fills its host and is never remeasured when the top/bottom chrome or audio controls change; controls overlay. The R181 `updateChromeLayout` changed stage top/bottom margins (48dp and up to 201dp), causing content scale jumps; R183 eliminates that geometry mutation and avoids decor window-insets toggles on every tap. `TextureView` uses stable transform and updates on surface size changes. This prevents the specific layout-induced resizing, not proof of Samsung 120 Hz parity.
2. **Direct video-thumbnail selection**: Tap a video tile in the shared bottom `GalleryRail` to enter VIDEO time-frame strip (if another video is tapped, first select it). The old always-visible '영상 탐색' button is hidden; a `‹ 목록` return control appears only inside time-strip mode. Other photo taps/select/swipes continue to navigate media.
3. **Real time-seek**: During horizontal time-strip motion, only the preview playhead/visible frame thumbnail updates; on release send ONE native `MediaPlayer.seekTo(targetMs, SEEK_CLOSEST)` and process `OnSeekComplete` to resume if originally playing. R181 called `seekTo` repeatedly ~every 150 ms during drag and could trigger decoder stalls/error; error reproduction seen in private R181 recording. Android API docs: seeks asynchronous and can queue most recent; see https://developer.android.com/reference/android/media/MediaPlayer .
4. **Frame thumbnails**: generated by `MediaMetadataRetriever` on dedicated background thread, selected near current position first; cache small previews and avoid large network/storage allocations on gesture frames. User cannot assume that preview extraction succeeds for every proprietary HDR/HEVC codec.
5. **Smoother mixed rail**: avoid clearing/rebinding photo ImageViews on same page ID; de-duplicate pending thumbnail loads; avoid destroying/recreating current player when merely tapping selected photo. All source media remain untouched.
