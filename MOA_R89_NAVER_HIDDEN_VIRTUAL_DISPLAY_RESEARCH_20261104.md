# MOA R89 Golden — NAVER Maps truly background favorites research / VirtualDisplay feasibility (2026-11-04)

## User request (do not substitute mere auto-return)
User asks specifically whether NAVER Maps can be made to **believe a screen exists and is showing the app** while automation actually runs **on a hidden/offscreen display** so foreground activity never steals the user's real phone screen, not just launching NAVER visibly and auto-returning. This is an explicit research/design request, NOT approval to alter the R89 APK.

## Key novel research — do not say 'impossible'
1. Public open source `loyality7/headless-android-sdk` (default master, README), uses **Shizuku → shell-identity app_process UiAutomation → hidden trusted VirtualDisplay → launches third-party app on second display**, reads accessibility nodes, clicks and SET_TEXT on that display only, strict display-0 protections. Android 11+; verified Redmi/POCO Android 14 only, **NOT Galaxy S26 Ultra Android 17**. Locked phone test FAILED; screen-off unlocked untested; a few exceptions may briefly reveal app on display 0. Source https://github.com/loyality7/headless-android-sdk
2. Public `android-notes/ShadowAuto` uses shell `app_process`, virtual display, target app launch, UiAutomation/OCR and display-targeted input, user display remains usable. Source https://github.com/android-notes/ShadowAuto . More generic AI than needed; prefer deterministic existing NAVER save state machine.
3. `dayeonisme/navermap-converter` uses Playwright Chromium sessions/login and CSS selectors to save addresses to NAVER Maps from a local web app. The author marks actual current NAVER UI selector validation **still pending**, and ambiguous places unresolved. This is a no-Shizuku **web-route hypothesis** if Android can host an authenticated offscreen WebView or browser session. Neither Chromium Playwright desktop code nor existing login cookies transfer transparently to Android NAVER app. Source https://github.com/dayeonisme/navermap-converter
4. A third-party user report describes private bookmark READ endpoints and private WRITE requests failing with `ncaptcha token is invalid`: https://saramjh.github.io/naver-map-save-list-bulk-reorganize-guide/ . Treat as unverified anecdote, **not** a supported NAVER write API; no CAPTCHA bypass, no stealing/extracting NAVER cookies.
5. AOSP explicit virtual-display security limits: ordinary nonprivileged apps cannot freely launch other companies' apps on arbitrary private virtual displays. A shell-privileged service (Shizuku/user-authorized ADB) or system display entitlement is key; putting a translucent, 1px, or invisible window over current app is NOT equivalent and is unreliable. https://source.android.google.cn/docs/core/display/multi_display/activity-launch
6. Shizuku official instructions: no-root wireless-debugging startup Android11+, but requires starting again after reboot; service/permissions/OEM differences. https://shizuku.rikka.app/guide/setup/ . Galaxy S26 Ultra Android17 behavior unknown; no one has validated the actual NAVER application on hidden display in current project.

- Reuse current NAVER candidate address/place ID, local job queue, alias/memo/list and verification. No mass auto-saving on wrong POI.
- FIRST compile a read-only VirtualDisplay feasibility harness as a separate source experiment (not extra installed app final): display id !=0, shell-permission check, launch harmless app, tree read, click, phone foreground unchanged. Exit immediately if activity lands on display0, if keyguard active or auth prompt arises.
- THEN one user-approved, pre-existing NAVER test place, on secondary screen, verify actual list and memo after fresh NAVER reload; do not conflate BUTTON_CLICKED with SAVED. Cancel/cleanup on any mismatch; do not log raw login cookies or family media.
- Test on Galaxy Android17: virtual display security, NAVER launch, UI tree, text, save persistence, main screen no interruptions, phone lock/off, reboot/Shizuku expiry, OEM killing. No absolute guarantees.
- If Shizuku rejected or unacceptable, test isolated authenticated mobile NAVER web UI offscreen (WebView/Chromium), but avoid sharing NAVER-app credentials/cookies, keep sign-in only in NAVER origin, and note WebView timers/process background throttling.
- Fallback existing visible accessibility workflow, optionally auto-return, ONLY when truly invisible save fails and user approves. No screenshot-forged or unauthorized session/captcha circumvention.

## Decision
**YES the exact 'fake second screen' concept has real open-source implementations.** But the Android17/Galaxy+NAVER integration remains a prototype hypothesis, not tested/working in MOA. High-confidence avenue: Shizuku or user-authorized ADB shell + isolated VirtualDisplay + targeted UiAutomation; lower-confidence no-elevated-privilege avenue: headless web login session and browser DOM; direct unsupported NAVER-private write API is not recommended.
