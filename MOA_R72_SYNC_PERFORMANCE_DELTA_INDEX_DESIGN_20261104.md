## Source-verified bottlenecks
1. Distributed R72 APK `assets/web/family-diary.js` `open()` is `render(); await init(); await refreshCuratedFromDatabase(); render(); mmR60RefreshMedia('diary-open')`. `init()` reads `entries` and `curated`, cached `meta/photo-index`, cover cache and thumbnail cover cache; `refreshCuratedFromDatabase()` then calls `dbAll('curated')` **again**, and `mmR60RefreshMedia` invokes `loadIndex(false)`.
2. Same JavaScript `loadIndex(false)` always posts `NativeHost.diaryIndex` to original HostActivity even when valid cached index exists. Original `androidHost/app/src/main/java/com/juhyeon/familyjourney/HostActivity.java` implementation `diaryPhotoIndex(int request)` queries **the entire MediaStore image library** sorted by DATE_TAKEN ASC, sends batches of 160 JSON items via `__fjDiaryChunk`, then iterates all videos, and only on final `done=true` does JS swap `S.photos` / `S.videos`. Prior user R61 local diagnostics had approx **13,126 photos + 983 videos** (historical, not necessarily current count). The bundled R72 `classes2.dex` contains matching `diaryIndex` / `__fjDiaryChunk` bridge strings.
3. HostActivity uses **one** `Executors.newSingleThreadExecutor()` for `diaryPhotoIndex`, thumbnails and other photo/EXIF work, potentially causing serialized queueing. `diaryPhotoIndex` also retrieves `getSharedPreferences(...)` inside the per-row loop. These are concrete targets for profiling but not measured causation for a specific user's delay.
4. R63 direct writer already saves the captured **photo id and exact timestamp and memo** into original IndexedDB `familyjourney-diary-v1/curated` and reads back before ack. The selected diary JS then waits for **another all-library metadata scan** to resolve that known ID into `S.byId` to show a thumbnail/card in the calendar. For native-memo captures, this is unnecessary for the *first optimistic calendar display*.

## Two-stage NONREGRESSIVE acceleration proposal (do not ship untested)
**Stage A: Immediate selected-photo diary fast path, JS/display-only; no core native write changes.**
- After loading `curated`, obtain new trusted photo/video ID and `at` from `moments[{at,photoIds,note}]` inserted by R63 writer; if missing from cached `S.byId`, overlay temporary in-memory `S.byId` item preserving the **original capture timestamp** and video prefix. Display count/selected photo timeline/thumbnail immediately using the existing MediaStore-ID thumbnail request without waiting for a 13k full index. Do NOT modify stored `curated`, `meta/photo-index`, 5-min groups or the writer HTML.
- Keep full media reconciliation in the background for other gallery photos, deleted media, manual picker and automatic photo calendar. If thumbnail fails/missing MediaStore ID, gracefully show placeholder and reconcile. Cancel stale async refresh after calendar switch/close; do not restore deleted/excluded records.
- Remove duplicate `dbAll('curated')` only if a reliable change generation/ack or diff exists; naïvely skipping it can miss late native commits.

**Stage B: True MediaStore DELTA index for dramatic backend gains.**
- Android API 30+ documented `MediaStore.getGeneration(context,volume)`, `MediaColumns.GENERATION_ADDED/MODIFIED` + `MediaStore.getVersion(context,volume)`. After trusted full baseline, track per-volume version/generation; on subsequent returns query **only new/changed** media rows rather than all 13k+; send `diaryIndexDelta` and merge by ID while preserving old index. Full scan on version mismatch, permission/volume change, reset, explicit user rescan and periodic deletion audit. Ensure `IS_PENDING` files not prematurely acknowledged, deterministic capture/added dates preserved, video and PC imports covered, dedupe by ID and stale entries corrected. Do not make time/current date guesses.
- Separate gallery thumbnail/EXIF workloads from high-priority incremental metadata query and instrument `native commit → curated IDB ack → first calendar preview → media delta completed → thumbnail ready`. Measure on Galaxy before promising concrete ms speedups.
- Target a *reduction in repeated scan work* from entire gallery (~13k images per open) to only new/modified rows (often 1–few), not an unverified promise of 0-ms full user-visible sync.
