## Proven code flow

1. **The caller DOES package photo address**: `fj-naver-favorites.js` `saveFromDiaryGps()` reads photo GPS and cached/reverse-geocoded `address`; `tryR289Offscreen()` then composes `{placeName,listName,address,alias,memo,placeId}` and sends `naverWebProbeControl('phone_submit:'+JSON.stringify(req))`. The request does **not** include a unique existing folder/shareId or photo lat/lon; the latter is used locally to derive address.
2. **Actual observed 16s fail gate is even earlier:** `tryR289Offscreen()` polls `phone_status`. After eight 2-second polls with `status === 'QUEUED'`, it emits `WEB_NO_FRAME_ACK`. This **does not prove** the top NAVER document acknowledged the job or performed LIST. The visible web page and persisted login do not substitute for `PARENT_TASK_RECEIVED`.
3. **Even if the parent receives the request, phase graph is structurally impossible:** `moa-r231-naver-frame-probe.js` parent `window.message` handler sets `setPhase('LIST')` (line ~130), transitions to SEARCH ONLY on a received child `LIST_READY` event (line ~134); but the actual child `async function list()` (lines ~225-241) has NO `report('LIST_READY')` path. It exclusively terminates with `LIST_ID_REQUIRED`, `LIST_DUPLICATE_NAME` or `LIST_NOT_FOUND_NO_CREATE` (or returns no status for mismatched legacy iframe). **There is no normal route LIST → SEARCH → SAVE.** R305 is intentionally a read-only diagnostic, not an automatic writer.
4. **A second liveness defect would invalidate a simple LIST-first reorder fix:** Search uses `location.replace('https://map.naver.com/p/search/'+encodeURIComponent(...))` in the parent (lines ~143-149), which reloads the top page. On every new top document, the code executes `sessionStorage.removeItem('moa.r237.pending')` (lines ~120-123) and never restores it; in-memory `task=null` on reload. Therefore an attempted SEARCH navigation would discard the job unless native-side job rehydration, one-time reload-safe persistence and de-duplication are implemented.
5. **No unique destination folder identity:** `tryR289Offscreen` task contains `listName` only, not folderId/shareId. The user's same-title '내 장소' duplicates mean that name alone cannot safely choose the user's 185-item original folder. The R301 safety ban on creating a new folder is correct and MUST remain.
6. **Stored star state cannot be attributed to this user tap:** Only the SAVE stage's `saveEntry()` clicks a *place-specific* star. Since the R305 LIST child cannot emit LIST_READY, no photo-specific SAVE stage is normally reachable. At most the LIST root may click the top NAVER '저장' navigation menu; the star already visible later might reflect an unrelated earlier manually saved place. No account write/readback evidence.

## Correct minimum next implementation, without guessing or changing the goal

1. **One jobId, one saved-photo target, and durable native lifecycle across navigation**. Every event needs a stage + nonce and clear ACK: `NATIVE_ACCEPTED`, `PARENT_ACK`, `ADDRESS_NAV_STARTED`, `EXACT_PLACE_RESOLVED`, `FOLDER_ID_BOUND`, `PLACE_SAVE_DIALOG_OPEN`, `FOLDER_SELECTED`, `ALIAS_MEMO_SET`, `SAVE_COMMIT_CLICKED`, `READBACK_VERIFIED` (no false PASS for UI clicks).
2. **Search the photo's verified address FIRST** in the same user-authenticated first-party WebView, distinguish exact address versus business; if ambiguous, request one user choice. Preserve job across top navigation; no automatic stale replay after failures.
3. **List resolution by first-party unique folder/shareId, explicit user selection of the original existing folder**, local private pin and re-validation on each run. Never choose by duplicate title or nonzero count; never create/delete a list from the normal save action.
4. After exact address/place target identified, **click the place-specific Save star, not top-left Saved nav tab**, choose the explicitly pinned ID, set alias/memo without clipping, commit once, and independently read back exact folderId + placeId/address + alias + memo from the authenticated account.
5. If a stage has no ACK, return the exact missing stage and ABORT, **no repeated click, no new folder, no success toast**. Foreground existing NAVER save and R269 Golden untouched.
6. A new APK must pass static finite-state test proving SEARCH reachable with nonce preserved through navigation, then a real Galaxy verified account place→folder→memo readback. **No final APK or production success was created by this source audit.**
