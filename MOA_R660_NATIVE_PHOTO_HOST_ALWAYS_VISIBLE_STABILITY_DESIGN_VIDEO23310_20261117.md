## Original uploaded Golden source — actual code-level failure surfaces
The user's exact R657 APK (SHA256 `f8c0e460ecacc7ab6d5a9a7c41dcee5e6fa8f25c94554c446c814ec983d6861a`) and R660 functional JS are byte-identical; exact source `assets/web/moa-r483-vertical-calendar.js`:
1. Lines 334–434: `r507StartInline` increments `r507Generation`, records `START_INLINE` synchronously, schedules async `tryOpen()` and silently returns on generation/page/hidden abort. A new `START_INLINE` before prior tries resolve can invalidate the pending generation. Only after bridge+valid IDs+connected stage does it set `__moaR511InlineArm=true`; waits for Java `__moaR511NativeArmed`; after 8s invokes `r594Fallback('NATIVE_ARM_TIMEOUT')`. Thus START_INLINE alone ≠ Java request.
2. Lines 45–102: `r596ScheduleWeb` at +5600ms when unmounted, `r596ShowWeb` unmasks WebView controls and rail; `r594Fallback` removes native owner classes and announces fallback text. This explains exactly why old 5-button viewer and warning appear; the log lacks the specific triggering reason.
3. `r507StopInline()` lines 304–316 increments generation/clears flags and, if opened, calls original `MoaLocalAudio.closeNativeGallery()`. `render()` at ~1558 calls stop when `r507Opened`, followed by `view.replaceChildren()`; this is dangerous when navigation/QR triggers full photo-day rerender during native host ownership. It is not proof that this exact path occurred in this video.
4. R592 specific `r592RefreshVisibleDay()` implements hot updates after native QuickRecord commit only while matching same day and active view; other calendar/day/hydrate paths are different.
5. Manual `__moaR543RepairInline`, native lost callbacks and fallback each cause re-arm/restart in different circumstances, and some are limited by attempt caps; manual retry is NOT a user-facing stability solution.
6. Actual original Java native owner (from Golden class `MoaR507InlineGalleryProvider`) gates Activity resumed/focus, native host open, attached photo DOM stage, onPreDraw, a shared `processing` boolean across asynchronous WebView snapshot callbacks. Earlier **R655** physically had 61 MAYBE_ARM_DENY_PROCESSING but is **not current R660 proof**. A distinct R657 bounded Java source was compiled in GitHub CI but is **not** the user's Golden R657 binary; do not mix or ship untested replacement.
7. Cached old app assets on same package persist across update. User actual R660 **cache-clear+restart** restored initial native Gallery, proving runtime/caching confound; does not prove exact cache entry or that QR failure is cache.

## Stable architecture acceptance contract, release must be physical device tested
**Single deterministic native PHOTO owner state machine** for each foreground PHOTO day with valid media:
- States: IDLE (page not active/no media), WAIT_MEDIA (hydration only), WAIT_STAGE (stable connected stage), ARM_REQUESTED (exact JS generation+day+Activity epoch), ARMED (Java preDraw ACK), OPENING (original Gallery opened), MOUNTED (native host attach + eight action deck ACK), SUSPENDED (app background, retain owner without new close/reopen), RECOVERABLE_FAIL (explicit reason), EXITED (deliberate user exit). Every transition records a reason and timestamps, no opacity.
- **Idempotent ensureMounted()** instead of repeated `r507StartInline` increment. A second QR/media-refresh event updates content/playlist on same host; does NOT cancel a healthy in-flight ARM/open or call close. If old day changed, hand off exactly once with explicit old owner finalization and new generation. Back user intent remains intact.
- Separate **photo UI stage lifecycle from story/photo-media data rendering**: keep card root DOM and native overlay stable; `r592RefreshVisibleDay` works on every QR return path including locked/Activity resumed; update original native playlist and story *in-place*. Never `replaceChildren` or `r507StopInline` on same day/owner merely due to media hydration/new QR commit.
- Native Java provider must own generation-safely bounded async processing callback and timeout (releasing only stale evaluation lock, never closing playing Gallery), page/activity focus epoch, preDraw attach and explicit denial reasons. No repeating WebView evaluateJavascript hot-path diagnostic on each tick; emit to native bounded ring buffer and export alongside Settings diagnostic. **First identify current gate with full R660 trace** before applying Java hot-patch.
- On foreground/day entry after actual host loss: first check original `Gallery.isOpen()`, host parent and attachment; if healthy, rebind geometry/preserve video frame and eight-action rail, never reopen. If truly absent, queue one native ARM→OPEN→MOUNT transaction after stage layout. Retry only with explicit denial/timeout, bounded backoff, epoch validation, and no competing owner. Do not impersonate user Back.
- No old WebView 5-action interactive legacy viewer while a native transaction is pending. Hold a stable captured poster/static fallback to avoid blankness; display non-intrusive error only after confirmed terminal failure. Do not hide photos permanently if Android host unavailable, but do not demote while it is attaching.
- On APK update, invalidate only WebView resource cache once per installed version (on the UI thread before loading index), and version-tag JS/CSS assets; preserve IndexedDB, LocalStorage, cookies, media IDs, Naver auth and installed signer. Official WebView.clearCache(true) clears resource cache, NOT user storage; do not call `WebStorage.deleteAllData`, delete databases or reinstall.
- User-approved **R657 real physical functional Golden remains immutable**, same signer/package, all original 8 native actions and existing records. New changes only on isolated feature branch; changed source/dex list, same-signer v2/digest and strict native owner/OneHand/QR QA; higher version forward *user-R657-functional* recovery prepared. Never make claims of universal success before actual Galaxy tests.
